# v2.0 Plan — Roadmap Construction

Multi-version strategic re-audit after v1.5.0 shipped. Output of this session is
this document; per-version charters and implementation work happen downstream in
local Claude (Cursor) per the hybrid pattern in `CLAUDE.md`.

## What this audit found

The v1.1 → v1.5 arc built the toolkit's foundational primitives: onboarding,
reliability, catalog depth, AI coherence, UX polish. The pipeline now writes
honest, verifiable metadata to a 5K-book library with structured telemetry, a
calibration measurement loop, cross-step coherence checks, and a discoverable
CLI/TUI surface. Test suite stands at ~460 hermetic tests.

The next wave is less "add the missing primitive" and more "close the loops the
primitives opened." Three big open loops surface from the audit, plus a smaller
fourth:

1. **LC catalog is dormant.** Item 12a has been parked since v1.3 — Cloudflare
   blocks every Python HTTP request to LC, and the OL edition cascade (the v1.3
   workaround) is now the dominant per-book cost at ~25s/book. Either restore
   LC reachability, optimise the OL fallback, or formally drop LC.

2. **Calibration data exists but doesn't feed back.** Item 17 closed the
   measurement loop; nothing closes the *action* loop. Per-tier precision is
   observable but rule edits, re-grades of stale writes, and trajectory views
   across sessions are all manual.

3. **Outputs aren't self-auditable at library level.** Per-book provenance is
   honest, per-batch summaries are clean, but there's no "how good is the whole
   library now" or "what did this session change" surface.

4. **v1.5 release-week observations.** PR #30 utf-8 fix is unreleased on main,
   the `Prompt.ask` discoverability issue surfaced in the triage memo, and the
   flag-standardisation sweep missed `clean-titles --dry-run`. A tight cleanup
   cycle absorbs these before the bigger work begins.

## v1.6 — Release-week follow-ups

### Release strategy for PR #30

PR #30 (the 10-line stdout/stderr utf-8 reconfiguration for legacy Windows
console) landed on `main` after v1.5.0 shipped and is currently unreleased.
Two ship paths:

- **v1.5.1 standalone.** Faster availability of the Windows fix. Establishes
  patch-release discipline. Costs a tag, a Release, and a CHANGELOG entry.
- **Roll into v1.6.** Ship alongside the rest of the v1.6 batch. No extra
  release overhead. Fix arrives a few weeks later.

**Recommendation: roll into v1.6.** The solo maintainer is presumably already
running off `main` locally, so the fix is functionally in service. v1.6 is the
next planned release anyway, and patch-release discipline doesn't earn its
keep on a single-user project.

## v1.7 — Catalog Reach, Take 2

Theme: resolve the dormant LC pipeline one way or another, then exploit the
OL fallback for everything it can do. End-of-cycle hit rate should be
substantially above the v1.3 baseline on the maintainer's mixed UK/US
literary-fiction library.

### Items

**1. Resolve item 12a — LC Cloudflare workaround.**

*Motivation.* Every LC HTTP request from the toolkit has been failing
since the start of v1.3 (`docs/LC-Cloudflare-Investigation.md`). Item 8's
honest source attribution means users see this, but the `lc_catalog` path
has been doing zero useful work. This item picks one of: `curl_cffi`
(browser TLS impersonation), OAI-PMH (LC's harvester endpoint, likely
not behind Cloudflare), or formally drop LC. Whichever wins, ship the
implementation and verify against a real batch.

*Touch points.* `services/lc_catalog.py` (entire file ~400 lines);
`pyproject.toml` for any new dependency; `docs/Getting-Started.md`;
`docs/LC-Cloudflare-Investigation.md` (mark resolved).

*Sizing.* L. *Risk.* high — Cloudflare evolves, all workarounds are
fragile. The "drop LC entirely" option is L for the code cleanup but
removes the risk.

*Dependencies.* Blocks items 5, 6, 7 below. The decision-and-verify
should be the cycle's first PR.

**2. OL edition cascade: in-cascade request parallelism.**

*Motivation.* When the OL cascade fires, sibling-edition ISBN lookups
inside one book run serially. The outer book loop in `modules/lcc.py` is
already parallel across books, but each book's cascade is single-threaded.
Parallelising the inner cascade should cut the ~25s/book floor measured
in probe runs noticeably.

*Touch points.* `services/lc_catalog.py:lookup_book` and the
`lookup_by_isbn_with_edition_cascade` path (added in item 12, PR #12).
Use `concurrent.futures.ThreadPoolExecutor` per book with a small worker
count (3–5) — same pattern as item 6's identifier loop.

*Sizing.* M. *Risk.* medium — care needed not to overwhelm OL with
concurrent requests from many books at once.

*Dependencies.* none, but compounds with items 3 and 4.

**3. Pre-fetch full editions list per work.**

*Motivation.* Today the cascade fetches sibling-edition info one ISBN at
a time. OL's `/works/{key}/editions.json` returns all known editions of a
work in one call. Switch to it; trade many small calls for one larger one.

*Touch points.* `services/lc_catalog.py` cascade implementation.

*Sizing.* S. *Risk.* low. *Dependencies.* compounds with item 2.

**4. Cross-run work-key cache persistence.**

*Motivation.* Resolving "this ISBN belongs to OL work XYZ" is stable
between runs. Today the cache is in-memory only — every fresh run redoes
the resolution. Persist to disk so a re-run on the same library skips
the lookups it already did.

*Touch points.* `services/lc_catalog.py` cache logic; new persistent
file at `~/.calibre-toolkit/ol-workkey-cache.json` with a TTL (e.g. 90
days).

*Sizing.* S. *Risk.* low. *Dependencies.* none.

**5. Combine catalog hits with description-grounded summaries.**

*Motivation.* When OL catalog has a real hit,
`_build_catalog_suggestion` (`modules/lcc.py`) writes a terse template
summary like *"Classified by Open Library under PR - English
Literature."* — accurate but thin. The AI-with-description fallback path
produces rich prose. Combine: when we have BOTH a catalog hit AND a
prefetched description, run AI only for the `lcc_summary` prose, keep
the catalog-derived `lcc` / primary / secondary fields. One extra small
AI call per catalog-hit book; best of both paths. Parking-lot item from
v1.5.

*Touch points.* `modules/lcc.py:_build_catalog_suggestion`; possibly a
new `suggest_lcc_summary` method on `AIClient` in `ai.py`; `rules/lcc.md`
may need a summary-only prompt variant.

*Sizing.* M. *Risk.* medium — touches AI prompt structure, requires
re-testing.

*Dependencies.* logically follows item 1 (catalog hit rate determines
how often this fires).

**6. `lcc` field truncation when AI-only.**

*Motivation.* When LC is unreachable and the AI guesses a full call
number like `PS3553.O684 W37 2024`, the class letters are usually right;
the Cutter (`O684`) and year are educated guesses. Open product question
from `docs/LC-Cloudflare-Investigation.md`: should the field truncate
to the supportable portion (class letters only) when no catalog source
confirmed it, rather than write a falsely-precise full call number?
Worth re-asking once item 1 lands and the new hit rate is observable.

*Touch points.* `modules/lcc.py` write path; possibly `rules/lcc.md`
prompt instructions; `docs/LC-Cloudflare-Investigation.md` (update
resolution).

*Sizing.* S. *Risk.* low — but worth a deliberate decision rather than
a default.

*Dependencies.* depends on item 1's outcome.

**7. Catalog-source provenance in summary panels.**

*Motivation.* Now that there are multiple catalog sources (LC direct,
LC via SRU, OL edition cascade, OL direct ISBN), the end-of-run summary
should break out which source contributed which books. Today the
diagnostic line in `lcc.py` shows raw hit counts; the v1.5 structured
panel doesn't yet surface them.

*Touch points.* `summary.py:StepSummary` `extras` field (already
designed for per-step breakdowns — comments uses it for word count,
identifiers for `by_lookup_method`); `modules/lcc.py` end-of-run.

*Sizing.* S. *Risk.* low. *Dependencies.* none.

## v1.8 — Coherence depth & calibration loop maturity

Theme: turn the v1.4 measurement loop into an *action* loop. The user can
not only see when calibration drifts but also act on it — re-grade stale
writes, capture rule-edit intent, browse the audit log without grep.

### Items

**1. Subject coherence checking.**

*Motivation.* Today's coherence check (`coherence.py:31-43`) is
period-only — "comment mentions WWII, no period tag." Subject coherence
("book is about jazz but no jazz tag") was deliberately deferred in
v1.4 because false positives are worse than misses: too many ways for a
comment to mention a topic without it deserving a tag. Design a
precision-first variant: high-bar, low-recall, fire only when nearly
certain.

*Touch points.* `coherence.py` — new `check_subject_coherence` alongside
the existing `check_*_coherence` functions; possibly a new keyword map
file under `rules/`.

*Sizing.* L. *Risk.* high — this is the cycle's hardest design problem;
false positives kill trust. May ship as an opt-in flag before becoming
default.

*Dependencies.* none.

**2. `audit-confidence` first-run friction reduction.**

*Motivation.* Parking-lot item. The calibration command samples books
and asks you to grade. First run on a fresh library is the most
valuable but highest-friction. Smaller default initial sample
(e.g. 5/tier instead of 20/tier), high-tier-first grading order, or
partial trajectories after a handful of grades.

*Touch points.* `commands/audit.py` (~489 lines); specifically the
sampling logic and the session-summary block.

*Sizing.* S. *Risk.* low. *Dependencies.* none.

**3. Calibration trajectory visualisation across sessions.**

*Motivation.* Once `audit-confidence` has run a few times, multi-session
data exists in `~/.calibre-toolkit/calibration.jsonl`. Today there's no
view of "is the high tier getting more accurate over time?" A small
Rich sparkline or per-tier table comparing session-over-session
precision picks up trends.

*Touch points.* `commands/audit.py` new `trajectory` subcommand or
`--trajectory` flag; reads the existing calibration log.

*Sizing.* M. *Risk.* low. *Dependencies.* none.

**4. Re-grade workflow when a rule changes.**

*Motivation.* When you edit `rules/lcc.md` to fix a calibration miss,
every prior AI write is now stale relative to the new rule. Today
there's no way to find affected past writes and re-run them. A command
that takes a rule-change marker (or a date), finds books last touched
before the change, and re-runs just those books against the new prompt.

*Touch points.* New `commands/regrade.py`; reads
`~/.calibre-toolkit/audit.log`; reuses each step module's run path with
an explicit book-id list.

*Sizing.* L. *Risk.* medium — interacts with every step's run path;
re-grading produces new audit-log entries that need to be marked as
re-grades not original writes.

*Dependencies.* benefits from v2.0 item 3 (prompt versioning in audit
log) but doesn't require it — coarser "last touched before date X"
filter works without precise prompt hashes.

**5. Per-tier rule-edit prompts.**

*Motivation.* When `audit-confidence` finds a tier where precision
dropped below threshold, today it flags and stops. Surface a
"what would you change in the rule?" prompt at session end, capture
intent in a rule-revision log (`~/.calibre-toolkit/rule-revisions.jsonl`)
so a future architect pass can act on accumulated signal.

*Touch points.* `commands/audit.py` end-of-session block.

*Sizing.* S. *Risk.* low. *Dependencies.* none.

**6. Audit-log query CLI.**

*Motivation.* The audit log (`~/.calibre-toolkit/audit.log`) is JSONL,
one row per write, since item 4 (v1.1). Today you grep it. A small
read-only command — `audit-log show --session …`, `--field …`,
`--book-id …`, `--since …` — makes the history queryable without
shell hackery.

*Touch points.* New `commands/audit_log.py`.

*Sizing.* M. *Risk.* low. *Dependencies.* none — but item J below
(TUI sidebar) reuses the parsing logic, so extract a shared reader.

**7. Per-step warnings rollup in review-table header.**

*Motivation.* Today `html_warnings` and `coherence_warnings` surface
per-row in review tables. On a 50-book batch with 5 flagged books,
you scroll to find them. Add a header line above the table: *"5 books
have coherence warnings, 2 have HTML warnings."* Pre-scroll signal.

*Touch points.* Review-table builders in `modules/comments.py`,
`modules/tags.py`, `modules/lcc.py`.

*Sizing.* S. *Risk.* low. *Dependencies.* none.

**8. TUI "since last session" sidebar.**

*Motivation.* New item from the GUI/polish brainstorm. On TUI startup,
pull from `~/.calibre-toolkit/audit.log`: a small panel showing
*"Last session: 2 days ago. 47 books touched. Wrote LCC for 23,
comments for 18, tags for 47."* Ambient orientation without you having
to remember. Carries information the existing left panel doesn't —
passes the item 22 test.

*Touch points.* `tui/app.py` mount path (~`499-558`); shared audit-log
reader from item 6 above.

*Sizing.* M. *Risk.* low. *Dependencies.* item 6 — reuse the reader.

## v1.9 — Architecture refactor & TUI test coverage

Theme: the codebase is mature enough that the cost of architectural
inconsistency now exceeds the cost of refactoring. Big files split,
duplication consolidated, TUI gets its first hermetic tests. Pure-refactor
cycle — no behaviour changes.

### Items

**1. Migrate top-level CLI commands into `commands/`.**

*Motivation.* Parking-lot item. Item 17 created `commands/` with
`audit.py` as first occupant. Other commands' implementations live as
functions inside `modules/` (e.g. `run_comments_enrichment` in
`modules/comments.py`) called from inline `@app.command()` handlers in
`cli.py` (1250 lines). Extract each inline handler into
`commands/<step>.py`. Pure refactor; consistency win.

*Touch points.* `cli.py:169-1222`; new files
`commands/{clean_titles,enrich_identifiers,lcc_enrich,comments_enrich,
tags_enrich,tags_cleanup,tags_review,clean_identifiers,unflag_manual,
doctor,init,setup_columns,library_info}.py`; `modules/` functions
likely move alongside or get re-shaped.

*Sizing.* L. *Risk.* low (pure refactor) but the diff is big — ship as
one PR to keep the move coherent, with no behaviour changes touching
the same diff.

*Dependencies.* none, but should land before items 2 and 5 below so
they can target the new layout.

**2. Split `ai.py` per-step.**

*Motivation.* `ai.py` is 1323 lines because one `AIClient` carries
per-step prompt assembly, parsing, and validation for all five AI
steps. Split into `ai/lcc.py`, `ai/comments.py`, `ai/tags.py`,
`ai/authors.py`, `ai/identifiers.py` with the shared core (token
telemetry, retries, batching, JSON extractors) staying common in
`ai/_client.py`.

*Touch points.* `ai.py` (entire file); imports across every
`modules/*.py` and `commands/*.py`.

*Sizing.* L. *Risk.* medium — large diff, lots of imports, prompt
parsing logic is delicate.

*Dependencies.* item 1 should land first.

**3. Typed config object.**

*Motivation.* `config.json` is loaded into a plain dict in
`cli.py:80-94` and accessed by string key everywhere
(`cfg["lcc"]["model"]`, `cfg["anthropic"]["api_key"]`). Replace with a
Pydantic model. Config errors fail loudly at startup with line-precise
messages; IDE autocomplete works.

*Touch points.* `cli.py:80-94`; every `cfg[...]` access across
`modules/`, `commands/`, `services/`, `tui/app.py`;
`config.example.json` as the schema reference.

*Sizing.* M. *Risk.* medium — touches every module, but mechanical.

*Dependencies.* none.

**4. Hermetic TUI smoke tests.**

*Motivation.* TUI is fully manual-tested today; the test ritual in
`CLAUDE.md` explicitly notes the test suite verifies code correctness,
not feature correctness. Textual ships a `Pilot` harness that can drive
the TUI programmatically — "open the TUI, press k, verify the
tags-cleanup screen appears with the right buttons." Catches TUI
regressions without manual smoke tests.

*Touch points.* New `tests/test_tui_smoke.py`; reads `tui/app.py:340-690`
to script interactions.

*Sizing.* M. *Risk.* low. *Dependencies.* none.

**5. Shared review-prompt helper.**

*Motivation.* About a dozen near-duplicate `Prompt.ask` blocks across
the modules. The duplication is why v1.6 items 2, 6, and 8 each have to
touch 5–10 sites. Extract a shared helper `review.py` with one entry
point that takes a list of suggestions and returns the user's decision
plus filter scope. Future cross-cutting review-flow changes take effect
in one place.

*Touch points.* New `calibre_toolkit/review.py`; replaces blocks in
`modules/authors.py`, `comments.py`, `lcc.py`, `identifiers.py`,
`tags.py` (and the migrated `commands/` versions if item 1 has landed).

*Sizing.* M. *Risk.* medium — easy to over-abstract; constrain to the
exact pattern, don't try to generalise across `tags_review`'s
per-book flow.

*Dependencies.* item 1 should land first.

**6. `doctor` extension for audit & calibration logs.**

*Motivation.* Today `doctor` (`setup.py`) validates config, library
path, calibredb, API key, and the 14 custom columns. The audit log
(v1.1) and calibration log (v1.4) now exist as first-class state.
Extend `doctor` to verify they exist, are readable, parse cleanly, and
flag any corrupted lines.

*Touch points.* `setup.py` doctor command path.

*Sizing.* S. *Risk.* low. *Dependencies.* none.

**7. Side-by-side diff view for proposed changes.**

*Motivation.* New item from the GUI/polish brainstorm. For
`clean-titles` and `comments-enrich`, the review pane shows the
proposed value but doesn't visually call out what changed. A diff view
— old on left, new on right, deltas highlighted — lets you scan a long
batch and spot "this AI dropped the subtitle" or "this comment lost
the award context" without rereading both sides word-for-word.

*Touch points.* `modules/authors.py:_build_review_table` (~155);
`modules/comments.py` review pane builder; Rich `Columns` or `Table`
two-column rendering.

*Sizing.* M. *Risk.* low. *Dependencies.* benefits from item 5
(shared review-prompt helper) so the view fits a common shape.

## v1.10 — Cost, performance & scale

Theme: now that the architecture is clean, optimise. Measure first
(latency telemetry), then act (parallelism, caching, scale resilience).
Adds budget discipline so a misconfigured batch can't surprise you on
spend.

### Items

**1. Budget guardrail (preflight cost projection).**

*Motivation.* Token cost is reported at end-of-run via item 13's
telemetry. Add a preflight estimate at start-of-run: *"This batch will
use approximately 50K input + 12K output tokens ≈ $0.45 — proceed?"*
Config knob `usage.confirm_above_usd` (default ~$1.00). Stops a
misconfigured `tags-cleanup` from quietly burning $20 on a re-run.

*Touch points.* `usage.py` projection helper; each step module's
start-of-batch path; `config.example.json`.

*Sizing.* M. *Risk.* low. *Dependencies.* none.

**2. Memory streaming for 10K+ libraries.**

*Motivation.* Item 21 was cut from v1.5 because no memory pressure
surfaced at 5K books. Repromoted with an explicit measurement gate:
don't ship without a real reproducer. If a future bigger library shows
Rich-table collapse or peak-RSS pressure, the chunked-rendering fix
that was already designed is ready to ship.

*Touch points.* `modules/identifiers.py:275-323`;
`modules/lcc.py:602`; possibly Rich table-rendering helpers.

*Sizing.* M. *Risk.* low. *Dependencies.* gated on a reproducible
measurement showing the predicted bottleneck.

**3. Per-step latency telemetry.**

*Motivation.* Token telemetry exists; per-step elapsed time exists.
But there's no breakdown like "AI call took 12s, calibredb write took
3s, OL cascade took 25s." Instrument each subsystem so you can see
where time goes — informs which subsystem deserves the next
optimisation pass.

*Touch points.* `usage.py` (or new `timing.py`); plumb timing into
`ai.py` calls, `db.py` writes, `services/lc_catalog.py` lookups;
`summary.py:StepSummary` to render.

*Sizing.* M. *Risk.* low. *Dependencies.* none — but its output
informs items 4 and 6.

**4. Prompt-cache effectiveness alarm.**

*Motivation.* Cache hit-rate is reported per step in the v1.3
telemetry. If it suddenly drops — e.g. you edited a rule file that
invalidates the cache — you'd only notice when cost goes up. A
one-line warning when hit-rate falls below a baseline (e.g. <50% on a
step whose rolling average is >80%) catches the regression at the
moment it happens.

*Touch points.* `usage.py`; per-step summary panels.

*Sizing.* S. *Risk.* low. *Dependencies.* none.

**5. Description-prefetch cache persistence.**

*Motivation.* Item 11 added Google Books / OL description prefetch
(`services/book_description.py`). Today results aren't cached across
runs — re-running the same book pays the API call again. Persist to
`~/.calibre-toolkit/description-cache.json` with a TTL (e.g. 180 days)
so stale entries eventually refresh.

*Touch points.* `services/book_description.py`.

*Sizing.* S. *Risk.* low. *Dependencies.* none.

**6. Concurrent multi-step orchestration.**

*Motivation.* Today you run one step at a time. Some steps don't
share state — `lcc-enrich` and `enrich-identifiers` operate on
disjoint Calibre fields. A `pipeline` command that orchestrates
multiple independent steps in parallel on disjoint book sets. Only
safe where steps don't conflict; needs an explicit safety map.

*Touch points.* New top-level `pipeline` command in `commands/`;
reads a step-conflict matrix.

*Sizing.* L. *Risk.* medium — concurrent calibredb writes need
careful sequencing; SQLite is single-writer.

*Dependencies.* item 1 of v1.9 (commands/ migration) so the
orchestrator can compose commands cleanly.

## v2.0 — Self-audit & reproducibility

Theme: the toolkit becomes capable of explaining its own output.
Library-level health metrics, per-write provenance pinned to a precise
prompt version, replay of past sessions, snapshot/diff across time. The
flagship feature that justifies the major-version bump.

### Items

**1. Session report command.**

*Motivation.* The audit log records every write. A `session-report
[--session …]` (default: most recent) command produces a one-page
report: *"this session touched 47 books, wrote LCC for 23, comments
for 18, tags for 47. 3 skipped due to validation failures, 2 declined
at review."* Answers "what did I do yesterday?"

*Touch points.* New `commands/session_report.py`; reads
`~/.calibre-toolkit/audit.log` via the shared reader from v1.8 item 6.

*Sizing.* M. *Risk.* low. *Dependencies.* v1.8 item 6 (shared reader).

**2. Library health index.**

*Motivation.* A single number — or small dashboard — describing the
library's overall MQG completion, trended over time. *"MQG
completion: 73% (+4% this month)."* Lets you see progress at the
library level, not just per-batch. Persists snapshots to
`~/.calibre-toolkit/health-history.jsonl`.

*Touch points.* New `commands/health.py`; queries Calibre
`metadata.db` for MQG flag distribution per step; reads audit log for
trajectory.

*Sizing.* L. *Risk.* low — but the "what to measure" design is the
real work; ship behind a deliberate metric definition.

*Dependencies.* benefits from v1.8 trajectory work; not blocking.

**3. AI-prompt versioning pinned per write.**

*Motivation.* Each AI write was generated against some version of the
rules files. Today nothing records that. If you later change a rule,
you can't tell which past writes were against the old version. Hash
the rules at run time and record the hash in the audit log alongside
the write. Enables v1.8 item 4's re-grade workflow to know precisely
which writes are stale.

*Touch points.* `ai.py` per-call recording; `logging_config.py` audit
schema extension; `~/.calibre-toolkit/audit.log` schema versioning
(forward-compatible new field, old readers ignore).

*Sizing.* M. *Risk.* low (audit schema is append-only). *Dependencies.*
strengthens v1.8 item 4 but doesn't block it.

**4. Replay-from-audit-log dry-run.**

*Motivation.* Given a past audit-log session, can the toolkit
re-derive the same suggestions today? If yes, the work is
reproducible. If no, something changed — rule, model, source data.
A `replay --session …` command re-runs the AI calls for a past
session, compares to what was actually written, reports drift. Useful
for "did the v1.8 rule edit actually change anything in practice?"

*Touch points.* New `commands/replay.py`; reuses each step's AI call
path with explicit book-id list and historical rule hash (item 3).

*Sizing.* L. *Risk.* medium — touches every step's run path; output
shape needs careful design (drift summary vs. diff list).

*Dependencies.* item 3 above (prompt versioning) — without it, replay
can't pin to historical prompts and "drift" is ambiguous.

**5. Library state snapshot + diff.**

*Motivation.* Export current state of all MQG fields for all books to
a snapshot file. Snapshot again tomorrow. Diff. See exactly what
changed, including manual edits done directly in Calibre's GUI
between runs. Catches the case where the audit log doesn't tell the
full story (Calibre GUI edits don't pass through this toolkit).

*Touch points.* New `commands/snapshot.py`; new
`commands/snapshot_diff.py`; reads `db.py` for full field export;
serialises to `~/.calibre-toolkit/snapshots/<timestamp>.jsonl`.

*Sizing.* M. *Risk.* low. *Dependencies.* none.

**6. v2.0 readiness sweep.**

*Motivation.* The cycle's closing chore PR. Dependency audit (anything
still pinned to a 4-year-old version?), deprecation sweep (any
"removed in v2.0" markers in the code?), CHANGELOG re-roll into one
canonical v2.0 entry summarising the major-version arc,
`pyproject.toml` bump to `2.0.0`.

*Touch points.* `pyproject.toml`; `CHANGELOG.md`; spot audit across
the codebase for `# TODO v2.0` / `# deprecated` markers.

*Sizing.* M. *Risk.* low. *Dependencies.* ships last in the cycle.

## Parking lot — considered and deferred

Items the audit surfaced but that didn't justify a numbered slot. Each
records what would need to change to promote.

- **Multi-library support.** Today `config.json` has one
  `library_path`. Multi-library would generalise to a list with
  per-library overrides. *Why parked:* CLAUDE.md states solo
  maintainer, one ~5K library. No second library on the horizon.
  Promote if a second library appears (e.g. partner's collection, or
  a quarantine library for new acquisitions).

- **Pluggable AI provider re-abstraction.** Today the toolkit is
  Anthropic-only (deliberate per CLAUDE.md). A provider abstraction
  layer would re-enable OpenAI / local models. *Why parked:* explicit
  project decision. Promote only if Anthropic's pricing or capability
  story changes materially.

- **Pipx / installer packaging.** Today the toolkit is installed via
  editable pip from the source clone. A pipx-installable wheel would
  be smoother for non-developer users. *Why parked:* personal use,
  developer maintainer, source-clone install is friction-free for
  this user. Promote if the toolkit ever ships to others.

- **Browser/web UI.** A web frontend over the CLI would enable
  remote use. *Why parked:* TUI + CLI cover all current workflows;
  the maintainer works on the machine where the library lives.

- **Configurable Rich theme** (light/dark/accessible). *Why parked:*
  solo maintainer, terminal theme is stable; config surface not
  worth the maintenance cost.

- **`--explain` flag per suggestion** showing derivation chain. *Why
  parked:* largely covered by the existing source-notes column and
  v1.7 item 7 (catalog-source provenance in summary panels).

- **Compact-mode review tables.** Same goal as in-table filter (which
  was itself cut from the GUI brainstorm). *Why parked:* not enough
  signal that table density is a real friction point.

- **Sticky review-table header on scroll.** *Why parked:* depends on
  terminal scroll behaviour that can't be controlled portably.

- **Cumulative shell-session stats footer.** *Why parked:* overlaps
  with v2.0 item 1 (session report command).

- **Quit confirmation in TUI.** *Why parked:* annoying more often
  than it saves you on a single-user tool.

- **Resume mid-batch from checkpoint.** Considered during GUI
  brainstorm and rejected — the maintainer's habit is to re-run on
  interrupt and the checkpoint overhead doesn't earn its keep.

- **Undo last session.** Considered during GUI brainstorm and
  rejected for similar reasons — relying on the audit log + manual
  fix is acceptable in current workflow.

- **Search/filter within long review tables.** Considered during GUI
  brainstorm and rejected — current batch sizes don't justify the
  in-table filter UI.

- **Inline edit during per-book review across all AI-suggest
  commands.** Considered during GUI brainstorm and rejected — the
  current "skip and fix in Calibre" workflow is acceptable; the
  feature would be built but rarely used.

## Process notes

- Each item is a single focused PR off `main`. Branch naming follows
  the project convention (`feat/v1.x-<slug>` / `chore/v1.x-<slug>`).
- v2.0 items are L-heavier than earlier cycles; consider splitting any
  individual L item into two PRs at charter time if scope expands.
- Per-cycle charters under `docs/planning/` are drafted at the start of
  each cycle by web Claude, take this roadmap as input, and add
  shipping order + per-item sequencing detail. Local Claude (Cursor)
  executes the cycle from the charter without further courier work.
- Items can be cut, deferred, or rejected mid-cycle (v1.5 cut item 21
  and rejected item 22). The disposition lands in the CHANGELOG entry
  for that version, not silently.
- Promotion rule for parking-lot items: a future architect pass should
  re-evaluate parked items each cycle and explicitly note which
  remain parked vs. promote.
