# v1.5 Charter — UX Polish

## Theme

Display-only improvements closing out the pre-Beyond ROADMAP items
(items 19–22). No behavioral changes, no AI prompt edits, no new commands,
no architectural refactors. The goal is to create a clean visible surface
for the v1.6 deep re-audit and the next batch of 30–50 items.

## Items in shipping order

PRs land one at a time. Local Claude pauses after each merge for review and
explicit go-ahead before starting the next item.

### 1. Item 20 — Progress bars in `lcc-enrich` and `comments-enrich`

Branch: `feat/v1.5-progress-bars`

Adds `rich.progress.Progress` with `TimeElapsedColumn`,
`TimeRemainingColumn`, and `MofNCompleteColumn` to two step modules that
still print plain `[5/50] Looking up…` lines:

- `calibre_toolkit/modules/lcc.py`
- `calibre_toolkit/modules/comments.py`

Pattern source: `calibre_toolkit/modules/identifiers.py:275–290`. Copy the
pattern; do not extract a shared helper yet — three call sites is the
threshold, not two.

**Scope correction.** `ROADMAP.md` item 20 currently reads "port to the
identifier loop, lcc-enrich, and comments-enrich batches." The identifier
loop already received the pattern in item 6 (parallelise step 02), and
`authors.py` + `tags.py` picked it up alongside the tags-cleanup batching
pass. Real remaining scope is just `lcc.py` and `comments.py`. **Fold a
ROADMAP wording fix into this PR** — re-state item 20's scope to match
reality.

Risk: low. Display-only.

### 2. Item 19 — Per-batch structured summary panels

Branch: `feat/v1.5-summary-panels`

Replaces the one-line totals at the end of each step (`lcc.py:710` is
typical) with a structured summary panel:

- High / medium / low count applied per tier
- Skip reasons (already done, validation failed, declined)
- Per-method success for identifiers
- Per-category counts for tags
- Word count + cost (from item 13's telemetry)
- Elapsed time and session timestamp

Define the panel shape once (small dataclass + a Rich render helper), then
apply uniformly across step modules. Touch points: every step module's
end-of-run display path; `cli.py`.

Risk: low. Display-only.

### 3. Item 21 — Chunked rendering for large batches

Branch: `feat/v1.5-chunked-rendering`

Switches result-table rendering in `identifier_enrichment`
(`modules/identifiers.py:275–323`) and `lcc_enrichment`
(`modules/lcc.py:602`) from collect-all-then-display to chunked
(20–50 rows at a time) with generators.

**Cut candidate.** James decides after seeing item 19's diff whether
real-library batch sizes justify shipping this. The ROADMAP claim that "a
1000-book run can exhaust RAM" may never bite in practice. If real usage
shows no memory pressure, skip this item and document the cut in the v1.5
CHANGELOG entry.

Risk: low. Optimization-only; results identical.

### 4. Item 22 — TUI pipeline overview panel — *attempted, rejected*

Branch: `feat/v1.5-tui-overview` (commit `375835f`, PR #26 — closed without
merge, branch discarded).

Built as planned: a 5-row summary panel above the existing two-panel layout,
each row showing step number, name, progress bar, percentage, and a status
icon + verbal label. Tests added, suite green.

Rejected on live inspection against the real library. The new panel
duplicated the left-panel `ListView` (`tui/app.py` `StepItem` rendering),
which already showed step number, name, progress bar, and done/total/% in
the same vertical space. The overview's only additions — status icon
(●/◐/○) and verbal label — are inferable at a glance from the bar itself.
Net effect was lost screen real estate for the actions panel on the right
without added signal. **The pre-existing left-panel visualization was the
correct one to keep.**

This was a useful lesson about additive-UI items at this level of polish:
the question isn't "can this be added without breaking anything" but "does
this carry information the existing surface doesn't." For a future
top-of-screen pipeline view, the higher-leverage shape is a single-line
*cross-step* summary (e.g. `Pipeline: 1✓ 2◐ 3◐ 4○ 5○ · 2,431/4,872 books
fully enriched`), not a re-render of what the left panel already shows.

Risk: low. *Actual outcome: low-risk, low-value — caught at PR review by
running the TUI and seeing the two surfaces side by side.*

## Parking-lot delta

No items promoted from the "Beyond v1.5" pool. All three known candidates
remain parked:

- **Catalog-hit + description-summary combination.** Higher-impact than any
  v1.5 item, but the design space is wider and benefits from being scoped
  alongside whatever the v1.6 deep re-audit surfaces.
- **Subject coherence checking.** Still carries high false-positive risk;
  no high-precision-low-recall signal identified during v1.4 release week.
  Revisit during the v1.6 audit.
- **`audit-confidence` first-run friction.** Real user data needed to
  decide whether a smaller initial sample, high-tier-first grading, or
  trajectory visualization is the right intervention. Defer pending real
  audit-log signal.

Plus three items from the broader "Beyond v1.5" section that explicitly
stay parked: `commands/` subpackage migration (pure refactor),
catalog-lookup performance (needs measurement first), `lcc` field
re-evaluation (open design question).

## Out of scope for v1.5

- Behavioral changes to AI output
- AI prompt edits
- New commands
- Architectural refactors
- Performance work that isn't display-driven

## Definition of done

  the v1.5 CHANGELOG entry. (Item 21 was a cut candidate from the start;
  item 22 was attempted and rejected after live inspection showed it
  duplicated the existing left-panel visualization — see the item 22
  section above for the rationale.)

- CHANGELOG entry for v1.5.
- `pyproject.toml` version bump to `1.5.0` in a final `chore/v1.5-release`
  PR.
- Annotated `v1.5.0` tag at the release merge commit.
- GitHub Release published with notes mirroring the CHANGELOG entry.

Tag creation, tag push, and GitHub Release publication are done locally by
James after all PRs merge.
