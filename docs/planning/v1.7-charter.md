# v1.7 Charter — Catalog Reach, Take 2

## Theme

Resolve the dormant LC pipeline one way or another, then exploit the OL
fallback for everything it can do. The seven items split cleanly into three
tracks: one investigation-and-decision item that gates the others (item 1),
three OL-cascade speedups that are independent of that decision and compound
together (items 3, 2, 4 in shipping order), and three catalog-shape items
whose framing depends on item 1's outcome (items 6, 5, 7 in shipping order).

End-of-cycle hit rate on the maintainer's mixed UK/US literary-fiction
library should be substantially above the v1.3 baseline for books that carry
an ISBN. Books without a usable identifier remain pure AI regardless of
where this cycle lands on LC — see *Workflow expectations* below.

This is a catalog cycle, not an AI prompt cycle. The one AI-touching item is
item 5's summary-only call; item 6 changes a write-time truncation rule, not
the prompt. No new commands, no architectural refactors. v1.8 picks up
coherence depth; v1.9 does the `commands/` migration and extracts the shared
review-prompt helper.

### 2. v1.7 item 3 — Pre-fetch full editions list per work

Branch: `feat/v1.7-ol-prefetch-editions`

Today the OL cascade fetches sibling-edition info one ISBN at a time from
`/api/books?bibkeys=ISBN:…`. OL's `/works/{key}/editions.json` returns all
known editions of a work in one call. Switch to it; trade many small calls
for one larger one. Reduces total request count per book before item 2
parallelises what's left.

Ships before item 2 — fewer per-book requests mean item 2's parallelism
has a smaller surface to coordinate over, and the load profile against OL
is gentler.

*Touch points.* `services/lc_catalog.py` cascade implementation; the
`lookup_by_isbn_with_edition_cascade` path added in item 12.

*Sizing.* S. *Risk.* low. *Dependencies.* none; compounds with item 2.

### 3. v1.7 item 2 — In-cascade request parallelism

Branch: `feat/v1.7-ol-cascade-parallel`

When the OL cascade fires, sibling-edition lookups inside one book still
run serially even after item 3's editions-list pre-fetch (item 3 collapses
the *fetch-list-of-editions* step; per-edition record lookups remain
serial). The outer book loop in `modules/lcc.py` is already parallel across
books; each book's cascade is single-threaded. Parallelise with a small
`ThreadPoolExecutor` (3–5 workers) — same pattern as item 6's identifier
loop.

*Touch points.* `services/lc_catalog.py:lookup_book` and the
`lookup_by_isbn_with_edition_cascade` path. Care needed: the outer book
loop is already multi-threaded, so this multiplies concurrent OL load.
Tune worker count and consider a global semaphore if probe runs surface
rate-limit pushback.

*Sizing.* M. *Risk.* medium — care needed not to overwhelm OL with
concurrent requests from many books at once.

*Dependencies.* compounds with item 3 (which lands first) and item 4.

### 4. v1.7 item 4 — Cross-run work-key cache persistence

Branch: `feat/v1.7-workkey-cache`

Resolving "this ISBN belongs to OL work XYZ" is stable between runs. Today
the cache lives in-memory only — every fresh run redoes the resolution.
Persist to `~/.calibre-toolkit/ol-workkey-cache.json` with a TTL (default
90 days). Subsequent runs against the same library skip the lookups they
already did.

Independent of items 2 and 3; ships in the speedup track so the cache
starts collecting hits during the cycle's verification runs.

*Touch points.* `services/lc_catalog.py` cache logic; new persistent file
at `~/.calibre-toolkit/ol-workkey-cache.json`; cache-invalidation entry
in the doctor command if a stale-cache failure mode surfaces in testing.

*Sizing.* S. *Risk.* low. *Dependencies.* none.

### 5. v1.7 item 6 — `lcc` field truncation when AI-only

Branch: `feat/v1.7-lcc-truncate-ai-only`

**Framing tightened since the v2.0 plan.** A real-library v1.6 run showed
AI-only Cutters hallucinating in a structurally wrong way — e.g. the AI
proposed `PS3603.O773` for an author whose name starts with "Correia"
(a "Correia" Cutter is in the `C6…` range; `O773` belongs to an
"O…"-prefix author). The class letters are usually right; the Cutter and
year are educated guesses the AI cannot verify without catalog access.

Treat this as a deliberate "ship the truncation," not an open question to
revisit. The rule:

- When LC or OL provides a confirmed full call number, write it through
  unchanged.
- When the AI proposes a call number with no catalog source confirming it,
  truncate the `lcc` field to class letters only (e.g. `PS3603`). Keep
  the AI's class-letter reasoning in `lcc_summary`; drop the unverified
  Cutter and year from the structured field.

This applies regardless of item 1's outcome, but the shape of "no catalog
source" changes:
- *If item 1 keeps LC:* truncation fires when neither LC nor OL had a hit.
- *If item 1 drops LC:* truncation always fires on the AI-only path —
  with no LC to consult, "no catalog source confirmed" reduces to "OL
  didn't hit," collapsing the two-source branch into one unconditional
  trigger.

*Touch points.* `modules/lcc.py` write path (the AI-only suggestion path
feeding into the field-write step); possibly `rules/lcc.md` prompt
instructions to ask the AI for class letters separately from Cutter/year
so the truncation is a structured field-pick rather than a string slice;
`docs/LC-Cloudflare-Investigation.md` (update resolution to record the
truncation rule shipped in v1.7).

*Sizing.* S. *Risk.* low — deliberate scope reduction of what the field
asserts; less is more honest.

*Dependencies.* Depends on item 1's merge so the "no catalog source" path
is unambiguous. Should not grow review-prompt code (see v1.9 forward note
in *Sequencing notes*).

### 6. v1.7 item 5 — Combine catalog hits with description-grounded summaries

Branch: `feat/v1.7-catalog-plus-prose`

When the OL catalog has a real hit, `_build_catalog_suggestion`
(`modules/lcc.py`) writes a terse template summary like *"Classified by
Open Library under PR — English Literature."* — accurate but thin. The
AI-with-description fallback path produces rich prose. Combine: when we
have BOTH a catalog hit AND a prefetched description, run AI only for the
`lcc_summary` prose, keep the catalog-derived `lcc` / primary / secondary
fields unchanged. One extra small AI call per catalog-hit book; best of
both paths. Parking-lot item from v1.5.

Item 1's outcome shapes scope:
- *If item 1 keeps LC:* item 5 fires on LC hits AND OL hits.
- *If item 1 drops LC:* item 5 fires only on OL hits — narrower trigger
  surface, same logic. Simplifies the catalog-source branching.

*Touch points.* `modules/lcc.py:_build_catalog_suggestion`; new
`suggest_lcc_summary` method on `AIClient` in `ai.py`; `rules/lcc.md` gains
a summary-only prompt variant that takes the already-resolved class +
catalog source as context and produces only the prose field.

*Sizing.* M. *Risk.* medium — touches AI prompt structure; requires
re-testing the AI client and adds per-catalog-hit-book cost. The cost
delta is bounded by `enrich-identifiers` reach: only books that resolved
both an identifier *and* a catalog hit incur the extra call.

*Dependencies.* Depends on item 1. Should not grow review-prompt code
(see v1.9 forward note).

### 7. v1.7 item 7 — Catalog-source provenance in summary panels

Branch: `feat/v1.7-lcc-provenance`

Now that there are multiple catalog sources (LC direct, LC via SRU if it

If item 1 dropped LC, the source list reduces to OL paths only — the panel

*Touch points.* `summary.py:StepSummary` `extras` (no schema change —
already designed for this); `modules/lcc.py` end-of-run summary assembly.

*Sizing.* S. *Risk.* low. *Dependencies.* depends on item 1's outcome
(determines source list); independent of items 5 and 6.

## Sequencing notes

**Item 1 is the gate.** PRs 2–4 (items 3, 2, 4) can ship before item 1
merges, but PRs 5–7 (items 6, 5, 7) cannot start until item 1 is in. The
charter ships item 1 first so the cycle's structural decision is settled
early and items 5–7 can be scoped to the actual outcome rather than
hedged across both possibilities.

**Items 3, 2, 4 are the speedup track.** Item 3 first (collapses the
fetch-editions-list step), then item 2 (parallelises what's left), then
item 4 (cross-run cache). Item 4 ships in the speedup track rather than
last so its cache file starts accumulating during item 5/6/7 verification
runs against the real library.

**Items 6, 5, 7 are the catalog-shape track.** Item 6 first — simplest,
ships a deliberate truncation rule the v1.6 real-library run revealed is
needed regardless of how item 1 lands. Item 5 next — the M-sized change
that actually adds AI prose to catalog hits. Item 7 last — display-only,
folds the cycle's new source taxonomy into the summary panel.

**v1.9 forward note: `calibre_toolkit/review_prompts.py`.** v1.6 PR #34
created `review_prompts.py` with one function (`confirm_bulk_apply`).
v1.9 item 5 will fold the duplicated per-tier `Prompt.ask` blocks across
the five AI-suggest modules into the same module. **v1.7 items 5, 6, and
7 must not grow new review-prompt code that would need to migrate later.**
Item 5 adds an AI call but no new review surface (the catalog-hit path
already passes through the existing review pipeline). Item 6 is a write
truncation, not a prompt. Item 7 is display-only. If implementation
surfaces a need to touch review-prompt code, pause and surface it — the
right answer is probably to pull the v1.9 helper forward into v1.7,
not to add a second one.

**Cost watch on item 5.** Item 5 adds one AI call per catalog-hit book.
The total bill is bounded by `enrich-identifiers` reach (a book without
an identifier never gets a catalog hit and never triggers the extra
call), but the rate is sensitive to item 1's outcome — keeping LC raises
the catalog hit rate and therefore the item-5 call volume. If the v1.7
verification run against the real library shows the cost delta is larger
than expected, the item-5 prompt can be made stricter (shorter summaries,
fewer tokens) or the trigger narrowed (e.g. only when the catalog-derived
template is shorter than some threshold).

## Workflow expectations

**v1.7 improves catalog reach for books with an ISBN.** The v1.6
real-library smoke run (30-book sample) showed 13 books with no usable
identifier for catalog lookup. Those books remain pure AI regardless of
how item 1 lands — there is no ISBN to look up. v1.7's hit-rate
improvements apply to the ~57% subset of the sample that carries a
usable identifier.

**Implicit pre-step: run `enrich-identifiers` first.** The catalog cascade
needs an ISBN or other catalog-resolvable identifier to fire. The
recommended pipeline order has always been
`enrich-identifiers → lcc-enrich`, but v1.7's improvements make that
ordering load-bearing rather than nice-to-have. A library run that
skipped `enrich-identifiers` would see most of v1.7's investment land on
zero books.

**Post-release expectation framing.** When reporting on real-library
results post-v1.7, the headline should be "catalog hit rate on
identifier-bearing books," not "catalog hit rate across the whole
library." The latter is gated by `enrich-identifiers` reach, which v1.7
doesn't touch. (Improving identifier reach itself is an open future
question — not in v1.7's scope, not in the v2.0 plan beyond what's
already in `enrich-identifiers`.)
