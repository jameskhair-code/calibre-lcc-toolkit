# v1.9 Charter — Architecture refactor & TUI test coverage

## Theme

The codebase is mature enough that the cost of architectural inconsistency now
exceeds the cost of refactoring. The v1.1→v1.8 arc built every primitive the
toolkit needs; v1.9 pays down the structural debt those cycles deliberately
deferred. Big files split, duplication consolidated, the TUI gets its first
hermetic tests, config becomes a typed object.

**This is a pure-refactor cycle. No behaviour changes.** The risk shape is
inverted from a feature cycle: the danger is not "does the new behaviour work"
but "is the behaviour byte-identical after the move." Diffs are large, imports
churn, and "smoke test" means *prove the output is unchanged*, not *prove a new
feature works*. The Definition of Done is written around that.

Three items are high-blast-radius (touch many files): the commands/ migration,
the ai.py split, and typed config. They must be strictly sequenced — one PR
each, no overlapping diffs — or the rebases will eat the cycle.

No new AI behaviour, no catalog work, no new commands. The deferred display-layer
items (side-by-side diff view, the v1.8 warnings rollup / since-last-session
sidebar, the TUI selected-step highlight) are held for a later TUI/polish pass —
they cluster cleanly and several reuse the v1.8 audit-log reader.

  "audit.py only" — CLAUDE.md's "only occupant" line is now stale).
- `review_prompts.py` **already exists** (27 lines, one function
  `confirm_bulk_apply`) — item 2 *extends* it, it is not created from scratch.
- Typed config touches **only 3 files** that access `cfg[...]` (plan implied
  "every module") — item 6 is downsized accordingly. `pydantic>=2.5` is already

- The duplicated per-tier `Prompt.ask` apply blocks are real and substantial:
  27 `Prompt.ask` calls across `modules/`, with the high/medium/low apply block

- Each step module is ~19 private domain helpers to 1 public `run_*`

  The CLI handler is already the thin layer — heavy domain logic already lives
  in `modules/`. This drives the topology decision below.

## Migration topology (decided)

**Option 2 — move orchestration to `commands/`, keep domain logic in
`modules/`.** Each `commands/<step>.py` owns the Typer handler + the `run_*`
orchestration + the review/apply flow; each `modules/<step>.py` keeps pure
domain logic (schemas, validators, `_build_review_table`, `_catalog_lookup_batch`,
the canonical-CSV machinery, etc.). This mirrors the existing `services/` split
and the v1.8 `commands/audit*.py` / `commands/regrade.py` precedent.

The cut rule, applied per function: **if it prompts the user or writes to
Calibre, it is orchestration → `commands/`; if it transforms data, it is domain
→ `modules/`.**

Rejected: full collapse into `commands/` (Option 3). With lcc at 1189 lines /
19 helpers, collapse produces a single >1,200-line file conflating CLI flow with
domain logic, and the maximal diff in a cycle whose only verification is
"behaviour is identical" — the worst risk/reward shape for a refactor. **Forward
note:** a future cycle may revisit fuller collapse / streamlining if Option 2's
two-homes-per-step shape proves to carry friction; recorded as a deliberate
follow-up consideration, not scheduled.

Result of the migration:
- `cli.py` → Typer app + command registration only (collapses toward ~200 lines).
- `commands/<step>.py` → handler + `run_*` orchestration + review/apply.
- `modules/<step>.py` → pure domain logic, no user prompts.

## Items in shipping order

PRs land one at a time. Local Claude pauses after each merge for review and
explicit go-ahead before the next item. Merge-autonomy carries forward from
v1.8: **contained low-risk items (4, 5) auto-merge after green smoke; the
high-blast L-items (1, 3) and the touches-everything item (6) get a two-phase
pause + explicit review** — investigate/plan the move → report → go-ahead →
implement.

### 1. Migrate top-level CLI commands into `commands/` (anchor)
Branch: `chore/v1.9-commands-migration`

Extract each inline `@app.command()` handler from `cli.py` and its `run_*`
orchestration from `modules/` into `commands/<step>.py`, per the Option 2
topology above. Pure refactor; the duplicated `Prompt.ask` apply blocks move
*with* the orchestration into `commands/` (item 2 then extracts them from there).

*Touch points.* `cli.py:174-1486` (18 handlers); new
`commands/{clean_titles,enrich_identifiers,lcc_enrich,comments_enrich,
tags_enrich,tags_cleanup,tags_review,clean_identifiers,unflag_manual,
doctor,init,setup_columns,library_info}.py`; the `run_*` functions move out of
`modules/{authors,identifiers,lcc,tags,comments,clean_identifiers,tags_review}.py`
(domain helpers stay). `cli.py` keeps only the Typer app + registration.
*Sizing.* L. *Blast.* high. *Risk.* low correctness risk (pure move) but the
diff is large and import churn is wide — ship as ONE PR, no behaviour change in
the same diff. *Dependencies.* anchor; items 2 and 3 target the new layout, so
this lands first.
*Verification.* Full suite green; `--help` output unchanged for every command;
a real-library smoke run of one AI-suggest step confirms identical behaviour.

### 3. Split `ai.py` into an `ai/` package
Branch: `chore/v1.9-ai-split`

`ai.py` is 1440 lines: one `AIClient` carrying per-step prompt assembly,
parsing, and validation for all five AI steps plus the shared core. Split into
`ai/lcc.py`, `ai/comments.py`, `ai/tags.py`, `ai/authors.py`,
`ai/identifiers.py`, with the shared core (token telemetry, retries, batching,
JSON extractors, the `_run_batches_concurrent` machinery) in `ai/_client.py`.
Preserve the public import surface (`from .ai import AIClient` and the
per-step `suggest_*` methods) so callers don't churn — re-export from
`ai/__init__.py`.

*Touch points.* `ai.py` (entire file) → `ai/` package; verify imports across
`commands/*.py` (post-migration) resolve through the re-export.
*Sizing.* L. *Blast.* high. *Risk.* medium — large diff, prompt-parsing logic
is delicate; the per-step parse/validate code must move verbatim. Ship as ONE
PR. *Dependencies.* item 1 lands first (so imports point at `commands/`).
*Verification.* full suite green; a real-library AI-suggest run per affected
step (or at least lcc + tags + comments) confirms identical suggestions and
identical token-telemetry output.

## Sequencing notes

**The refactor spine is strictly ordered: 1 → (2, 3).** Item 1 (commands
migration) is the anchor; items 2 (review helper) and 3 (ai split) both target
the migrated layout. Do not start 2 or 3 until 1 has merged. Items 2 and 3 touch
different surfaces (review/apply flow vs AI client) so they don't conflict with
each other, but each is its own PR.

**The independent track (4, 5, 6) fills between the big refactors.** TUI smoke
tests (4) ideally land *before* item 1 so they guard against TUI drift during
migration. `doctor` (5) and typed config (6) can land any time; both are cleaner
after the migration but neither is blocked by it.

**One high-blast L-item in flight at a time.** Items 1 and 3 must never share an
open diff — finish and merge 1 before 3 opens. This is the cardinal rule of the
cycle; a rebase between two 1000-line refactor diffs is where a refactor cycle
goes to die.

**Import-surface discipline.** Both 1 and 3 must preserve public import paths
(`from .ai import AIClient`, the `run_*` callable surface the TUI uses) via
re-exports, so the TUI and tests don't churn alongside the refactor.

## Definition of done

A refactor cycle's DoD is behaviour-identity, not feature-correctness:

- All six items merged or shipped, with dispositions noted in the v1.9 CHANGELOG
  entry (Option-2 topology recorded; typed-config downsizing noted; deferred
  TUI/polish cluster recorded).
- `python -m pytest -q` green on `main` — and the suite is **at least as large**
  as before each refactor PR (no tests silently dropped in a move).
- For items 1 and 3: a real-library smoke run confirms **identical** output and
  token telemetry vs pre-refactor (the verification spine for behaviour-neutral
  work).
- `--help` output unchanged across all commands after the migration.
- CHANGELOG entry for v1.9.
- `pyproject.toml` bump to `1.9.0` in the final `chore/v1.9-release` PR.
- Annotated `v1.9.0` tag at the release merge commit.
- GitHub Release published with notes mirroring the CHANGELOG entry.

Tag creation, tag push, and GitHub Release publication are done locally by James
after all PRs merge.
