# v1.8 Charter — Coherence depth & calibration loop maturity

## Theme

Turn the v1.4 measurement loop into an *action* loop. Since v1.4,
`audit-confidence` can *show* you when confidence tiers drift from observed
accuracy — but you can't easily act on what it shows. v1.8 closes that gap:
re-grade stale writes after a rule changes, capture rule-edit intent at the
moment of friction, browse the audit log without grep, and see calibration
trends across sessions. Alongside, deepen coherence checking from period-only
to subject-level, and gate the one class of AI change (authorship) that can
silently corrupt data.

This is the hardest cycle of the v1.6→v2.0 arc: two risky L-sized items
(subject coherence, re-grade workflow), each carrying real design or
integration risk, each gated behind a two-phase pause. Scope is deliberately
held to a focused seven-item core — the calibration action-loop, subject
coherence, and author-change gating. Three display-layer items (the v2.0
plan's v1.8 items 7 and 8, plus the inbox TUI-highlight entry) are **deferred
to a later polish pass** so they don't dilute a cycle that demands careful
design work.

No architectural refactors (v1.9 owns the `commands/` migration and the shared
review-prompt helper). No catalog work (v1.7 closed that out).

## Items in shipping order

PRs land one at a time. Local Claude pauses after each merge for review and

below) additionally use a **two-phase pause**: prototype/design → report →

### 1. v1.8 item 2 — audit-confidence first-run friction reduction
Branch: `feat/v1.8-audit-friction`

The calibration command samples books and asks you to grade AI writes for
accuracy. First run on a fresh library is the most valuable but highest
friction — it asks for a large initial sample before showing anything useful.
Reduce it: smaller default initial sample (e.g. 5/tier instead of 20/tier),
high-tier-first grading order, and/or partial trajectories surfaced after a
handful of grades rather than only at the end.

*Touch points.* `commands/audit.py` sampling logic + session-summary block.
*Sizing.* S. *Risk.* low. *Dependencies.* none.

### 2. v1.8 item 3 — Calibration trajectory visualization
Branch: `feat/v1.8-calibration-trajectory`

Once `audit-confidence` has run a few times, multi-session data accumulates in
`~/.calibre-toolkit/calibration.jsonl`, but there's no view of whether a tier
is getting more accurate over time. Add a per-tier, session-over-session view
— a small Rich sparkline or comparison table — surfaced via a `trajectory`
subcommand or `--trajectory` flag.

*Touch points.* `commands/audit.py`; reads the existing
`~/.calibre-toolkit/calibration.jsonl`.
*Sizing.* M. *Risk.* low. *Dependencies.* none.

### 3. v1.8 item 5 — Per-tier rule-edit prompts
Branch: `feat/v1.8-rule-edit-prompts`

When `audit-confidence` finds a tier whose precision dropped below threshold,
today it flags and stops. Surface a "what would you change in the rule?"
prompt at session end and capture the intent in a rule-revision log
(`~/.calibre-toolkit/rule-revisions.jsonl`) so accumulated signal is available
for a future architect pass.

*Touch points.* `commands/audit.py` end-of-session block.
*Sizing.* S. *Risk.* low. *Dependencies.* none.

### 4. v1.8 item 6 — Audit-log query CLI
Branch: `feat/v1.8-audit-log-query`

The audit log (`~/.calibre-toolkit/audit.log`, JSONL since v1.1 — one row per
write, shape `{timestamp, book_id, field, new_value, confidence?, source?,
+extra}` per `logging_config.py:117-128`) is grep-only today. Add a small
read-only command — `audit-log show` with `--session` / `--field` /
`--book-id` / `--since` filters — that makes the history queryable.

**Enabler for item 4.** Extract a shared audit-log *reader* (parse + filter)
as part of this item; the re-grade workflow (PR 6) reuses it rather than
writing its own parser. Keep the reader cleanly separable — the deferred TUI
sidebar (v1.8 item 8) would also reuse it when it lands.

*Touch points.* new `commands/audit_log.py`; a reader module/function it and
item 4 share; `cli.py` command registration.
*Sizing.* M. *Risk.* low. *Dependencies.* none; blocks item 4 (PR 6).

### 5. Inbox item — Author-change review gating
Branch: `feat/v1.8-author-change-gating`

From the 500-book `clean-titles` run (2026-05-28): the AI removed an author
from "J R" (Joy Williams → William Gaddis only) on its own training knowledge,
marked medium confidence, and it auto-applied under "apply all." Authorship
deletions from model memory are a high-risk category that can silently corrupt
data. The same run showed the desired behaviour on "The Tree of Life" — it
*flagged* a suspicious pairing for verification rather than changing it. Make
author-field changes consistent: flag / review-gate rather than auto-apply at
medium+, and cap authorship *removals* at low/review-only.

*Touch points.* confidence-tier assignment for author-field changes in the
clean-titles path — `rules/` for authors + `modules/authors.py` tier handling.
*Sizing.* S–M. *Risk.* low–medium — changes confidence semantics for one field
class; the real-library smoke must confirm legitimate author fixes (e.g.
capitalisation, diacritic normalisation) still flow through unblocked.
*Dependencies.* none. Keep the tier-handling change minimal so v1.9's
review-helper extraction can absorb it.

### 6. v1.8 item 4 — Re-grade workflow when a rule changes (two-phase)
Branch: `feat/v1.8-regrade`

When you edit a rule (e.g. `rules/lcc.md`) to fix a calibration miss, every AI
write made before that edit is now stale relative to the new rule. Today
there's no way to find and re-run the affected books. Add a command that takes
a rule-change marker (or a date), finds books last touched before it, and
re-runs just those against the new prompt.

**Two-phase pause.** *Phase A:* design how re-grade audit entries are
distinguished from original writes, how the command reuses each step's run
path with an explicit book-id list, and the date/marker filter; prototype
against a small real batch; report. *Phase B:* build after go-ahead.

*Touch points.* new `commands/regrade.py`; reuses item 6's audit-log reader;
reuses each step module's run path with an explicit book-id list; writes
re-grade-tagged audit entries.
*Sizing.* L. *Risk.* medium — touches every step's run path; re-grade entries
must be marked so they don't pollute calibration as if they were original
writes.
*Dependencies.* item 6 (the shared reader). Ships after the calibration
cluster.

### 7. v1.8 item 1 — Subject coherence checking (two-phase, opt-in-first)
Branch: `feat/v1.8-subject-coherence`

Extend `coherence.py` from period-only (`_PERIOD_KEYWORDS`,
`check_comments_coherence`, `check_tags_coherence`) to subject-level — "the
comment discusses jazz but no jazz tag." Deferred from v1.4 because false
positives kill trust faster than misses. Design precision-first: high-bar,
low-recall, fire only when nearly certain.

**Two-phase pause.** *Phase A:* prototype `check_subject_coherence` + a curated
subject keyword map; run against a real comments/tags batch; show James the
false-positive rate. *Phase B:* build after go-ahead.

**Ships opt-in-first.** Lands behind a flag (default off). Promote to default
only if the real-library false-positive rate proves low enough to trust. If it
stays noisy, it remains an opt-in tool or slips to a follow-up — without
blocking the rest of the cycle.

*Touch points.* `coherence.py` — new `check_subject_coherence` alongside the
existing checks; likely a new subject keyword map under `rules/`; the callers
in `modules/comments.py` / `modules/tags.py` that surface coherence warnings
(behind the flag).
*Sizing.* L. *Risk.* high — the hardest design problem in the arc; false
positives are the failure mode.
*Dependencies.* none.

## Sequencing notes

**The calibration cluster (PRs 1–3: items 2, 3, 5) all touch
`commands/audit.py`.** Ship them consecutively so the audit.py edits land
coherently; each is additive to a different part of the file (sampling logic,
trajectory subcommand, end-of-session prompt). If two turn out to touch the
same lines, combine into one PR rather than churning the file twice (the v1.6
items-2+6 precedent).

**Item 6 → item 4 reader dependency.** Item 6 (PR 4) extracts the shared
audit-log reader; item 4 (PR 6) reuses it. Item 6 must merge before item 4
starts. Don't let item 4 write a second parser.

**Risky Ls last, behind two-phase pauses.** Items 4 and 1 (PRs 6 and 7) are
the risk concentration. They ship after the contained work is banked, each
with prototype-before-build. If item 1's prototype shows an intractable
false-positive rate, it ships opt-in-only or slips — the cycle still delivers
its calibration-loop spine regardless.

**v1.9 forward note.** v1.9 owns the `commands/` migration and the shared
review-prompt helper. v1.8 adds new commands (`audit_log.py`, `regrade.py`)
directly under `commands/` — consistent with where v1.9 will consolidate, so
no migration debt is created. The author-gating change (PR 5) touches
`modules/authors.py` tier handling; keep it minimal so v1.9's review-helper
extraction can absorb it.
